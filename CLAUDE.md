# MJP Marine CRM — рабочие правила для Claude Code

## Секреты и безопасность
- Секреты — в `.env`, ключи Google/FB/Telegram не коммитить.
- Проверка прав — на сервере, всегда; UI лишь прячет недоступное.
- Все мутации денег/склада/статусов → аудит-лог.
- Деньги — только через безопасную арифметику (целые центы / Decimal), никаких float.
- **Права в `app/api/crm/**` роутах** — только через `hasPermission(...)` с явным
  `return NextResponse.json({ error: 'Недостаточно прав' }, { status: 403 })`,
  или (предпочтительно для новых роутов) `requireCrmAccess(module, action)` из
  `lib/crm/apiGate.ts` одним вызовом. **Никогда не `requirePermission(...)`
  без try/catch** — она бросает исключение, а Route Handlers в App Router
  ничего не ловят вокруг тела хендлера, поэтому недостаточно прав тихо
  превращается в 500 вместо 403 (была реальная проверенная вживую проблема,
  почищено по всем роутам). `requirePermission` — throw-версия — годится
  ТОЛЬКО в Server Components (`page.tsx`), где Next.js рендерит ближайший
  error boundary и это ожидаемое поведение.
- Каждый защищённый модуль (`CLIENTS`, `FUNNEL`, `SCHEDULE`, `INVENTORY`,
  `FINANCE`, `INVOICES`, `REPORTS`, `SETTINGS`) должен быть покрыт тестом
  «неавторизованный доступ» в `tests/authz/unauthorizedAccess.test.ts` — при
  добавлении нового модуля/защищённого роута добавь туда запись.

## Тесты
- `npm test` (vitest, разово) / `npm run test:watch`. CI — `.github/workflows/test.yml`,
  гоняется на каждый push/PR против эфемерного Postgres (не продакшен-Supabase).
- `tests/cascades/*` — денежные каскады (recordPayment/refundPayment, списание
  и возврат склада, IVA, касса/доинвестиции, дебиторка, атомарная нумерация) —
  приоритет №1, любая правка в `lib/crm/services/invoiceCascade.ts`,
  `lib/crm/services/cash.ts`, `lib/crm/numbering.ts`, `lib/crm/services/ar.ts`
  должна остаться зелёной или обновить тест осознанно, не молча.
- `tests/authz/*` — неавторизованный доступ по каждому модулю (см. выше).
- `tests/helpers/rollback.ts` (`withRollback`) — для каскадов, принимающих
  `tx`: гоняет тест в транзакции и откатывает её в конце, ничего не остаётся
  в базе, безопасно даже против общей dev-БД. `tests/helpers/persistedCompany.ts`
  — только когда тестируемая функция читает через синглтон `prisma`, а не
  принимает `tx` (computeCashSummary, outstandingBalances, numbering под
  реальной гонкой) — создаёт/сносит настоящую throwaway-компанию, убирать за
  собой обязательно (`afterEach`/`afterAll`).

## Design reference
- Эталон визуала всех экранов CRM — папка `design/` в корне репозитория.
- Перед вёрсткой/правкой любого экрана CRM обязательно открыть соответствующие
  файлы из `design/` и верстать строго по ним.
- Имя файла = экран: `dashboard`, `clients`, `pipeline`, `planner`, `warehouse`,
  `finance`, `invoice`, `access`, `styleguide`, `login`, `setup`.
- Один экран может быть разбит на несколько файлов:
  - Суффиксы `-top` / `-bottom` (или `-1` / `-2`) — длинный экран по вертикали:
    собрать верх и низ в **одну** страницу, не делать два разных экрана.
  - Суффиксы `-week` / `-month` / `-day`, `-list` / `-detail`, `-empty` / `-filled` —
    разные виды/состояния одного экрана: реализовать все как переключатели/состояния
    внутри одного экрана.
- Данные — из Prisma/Supabase, **не** из моковых. Дизайн задаёт вид, база — данные.

1. В начале работы над экраном: `ls design/`, найти все файлы экрана.

### Каскад склад→касса: приход = расход, продажа = доход, капитализация (2026-08-30)
Приход на склад (`RECEIVE`) и продажа со склада (`SELL`) теперь двигают реальные
деньги, не только `qtyInStock`: приход — `EXPENSE` (категория `Закупка склад`,
кассе больно сразу — «купил за свои»), продажа — `INCOME` (`Продажа запчастей`,
уже было). Списание в работу (`WRITE_OFF`) и корректировка (`ADJUST`/`ORDER`)
деньги не двигают — списанное уже учтено в счёте клиенту, отдельная проводка
задвоила бы расход. Логика — общая функция `recordStockFinanceEntry`
(`lib/crm/services/stockFinance.ts`, `total.lte(0)` → ничего не создаёт, не
засоряет ленту нулевыми операциями), вызывается из веб-роута
(`app/api/crm/inventory/[id]/movement/route.ts`) и Mini App
(`app/api/tg/warehouse/[id]/movement/route.ts`) — раньше SELL был продублирован
в обоих файлах отдельно, RECEIVE в Mini App вообще не создавал проводку.
Без IVA (как и у существующего SELL) — сознательно просто, полный цикл с
НДС/статусом оплаты уже есть отдельно через Поставщики (`SupplierBill`).
Капитализация склада — `computeInventoryValuation()` (`lib/crm/services/
inventory.ts`), живой расчёт `Σ qtyInStock×costPrice` (сколько денег сейчас в
остатках) и `Σ qtyInStock×sellPrice` (потенциал), НЕ отдельная бухгалтерская
запись — меняется сам по себе с движением склада. Показано KPI-карточками на
`/crm/inventory`, спрятано за `FINANCE.VIEW` (это про деньги, не про остатки).
Тесты — `tests/cascades/stockFinance.test.ts`. Проверено вживую: приход 5×10€
→ `EXP-... Закупка склад −50€`, касса/P&L/дашборд отреагировали сразу; тестовая
проводка отменена штатным сторно (не удалением), остаток — через `ADJUST`.

## Стадии воронки (Pipeline)
`Новый лид → Контакт → Пресмет → Запланировано → Выполнено → Счёт → Оплачено`
Prisma-значения: `NEW_LEAD | CONTACT_MADE | QUOTE_SENT | WORK_SCHEDULED | WORK_DONE | INVOICE_SENT | PAID`

### Заметка по Этапу 8
- `/crm/reports` — выручка по маринам/видам работ (виды работ = категории
  `FinanceEntry(INCOME)`, отдельного поля «тип работы» в схеме нет), реклама по
  каналам + блендед CPL/ROMI (точная привязка канал→лид есть только для
  Facebook через `ClientSource`), топ-клиенты, дебиторка с просрочкой красным,
  KPI-цель план/факт (`KpiGoal`, редактируется прямо на странице).
- CSV-экспорт (`lib/crm/csv.ts` + `<ExportCsvButton>`): **headers/rows должны
  быть готовыми плоскими массивами (string|number), посчитанными на сервере**.
  Функции нельзя передавать из Server Component в Client Component («Functions
  cannot be passed directly to Client Components») — именно поэтому
  `ExportCsvButton` принимает `headers: string[]` + `rows: (string|number)[][]`,
  а не колонки с функциями-аксессорами. Не возвращать это оформление.
- FB Lead Ads — заготовка: настройки в CRM → Настройки → Facebook Lead Ads
  (App ID / Verify Token / Page Access Token, выключено по умолчанию), webhook
  `/api/crm/webhook/facebook` (GET — верификация, POST — принимает
  `leadgen_id` и дозапрашивает данные лида через Graph API с Page Access
  Token). Проверено вживую: verify handshake и graceful-ошибка на
  невалидном токене работают; создание клиента из реального лида не
  тестировалось — нет настоящего FB App/токена.
- Инпуты рядом с `type="password"` — ставить `autoComplete="off"` (соседним
  текстовым полям) и `autoComplete="new-password"` (самому паролю), иначе
  Chrome подставляет туда сохранённый email/логин пользователя (нашли на
  форме FB Lead Ads: поле App ID автозаполнялось email'ом админа).

### Заметка по Этапу 7 (важно для будущих правок бота)
- Сессии grammY (в т.ч. `@grammyjs/conversations`) хранятся в Postgres
  (`TelegramSession` + `lib/crm/telegram/session-storage.ts`) — серверлесс-инвокейшены
  не делят память между сообщениями одного диалога, in-memory session не переживёт продакшен.
- `conversation.external(...)` клонирует возвращаемое значение через `structuredClone`
  для журнала повторов. **Никогда не возвращать из него сырые Prisma-записи или
  Decimal** — оба не клонируются (`DataCloneError`). Возвращать только примитивы
  (строки/числа/булевы), конвертируя Decimal через `.toString()` заранее.
  См. `lib/crm/telegram/conversations.ts`.
- Привязка аккаунта: код генерируется в CRM → Настройки → Пользователи CRM
  (кнопка «Получить код», 15 минут), сотрудник отправляет боту `/link <код>`.
- Фото чека сохраняется как временная ссылка на Telegram CDN (`receiptUrl`), НЕ в
  Google Drive — SA credentials всё ещё не подключены (см. Этап 5). Когда появятся,
  перенести загрузку чеков туда же, где будет реализован Sheets sync.
- Локальный dev-тест бота без публичного webhook URL: см. `scripts/tg-relay.sh`-стиль
  скрипт — long-poll `getUpdates` и форвард апдейтов на `POST /api/crm/webhook/telegram`
  на localhost. Реальная отправка ответов через `bot.api.sendMessage` работает
  независимо от способа получения апдейтов.

### Починка Mini App / бота (промпт D, 2026-08-11)
Симптом: «нет кнопки открыть приложение, команды не работают». Диагностика
показала — код бота и Mini App (`app/tg/**`, `app/api/tg/**`) уже были
построены заранее (пред. сессия), проблема была в внешней конфигурации
Telegram и в паре реальных багов, найденных при сверке с промптами A/B:
- **Webhook не был установлен вообще** (`getWebhookInfo` → `url: ""`) — вот
  почему команды не отвечали: Telegram физически не знал, куда слать апдейты.
  Домен `mjpmarine.com` (алиас `mjp-marine.vercel.app`, 307 на кастомный домен)
  уже был живой и отвечал 200 на `/api/crm/webhook/telegram` и `/tg`.
- **Menu button был `type: "commands"`** (дефолт Telegram — просто список
  команд), не `web_app` — поэтому кнопки «Открыть приложение» не было вовсе.
- В `bot.ts` не было `bot.catch(...)` — ошибка в любом хендлере уходила в
  необработанный reject молча, без единой строки в логах.
- **Категории в боте читались из `ReferenceItem`** (`EXPENSE_CATEGORY`/
  `INCOME_CATEGORY`, сеялись в `seed-references.ts`) — отдельный список от
  `Category`, на котором работает весь веб (`CategoryCombobox`, импорт из
  промпта C). Новая категория, заведённая в вебе, боту была не видна. Бот
  переведён на `Category` (см. `pickCategory` в `conversations.ts`),
  `seed-references.ts` больше не сеет параллельный список.
- **`GET /api/tg/finance` считал кассу вручную** (`income − expense − salary +
  reinvested`) — так и должно было работать до промпта A, но после него это
  игнорирует IVA repercutido/soportado и удержанный IRPF, то есть показывает
  неверную кассу. Переведено на `computeCashSummary()` — тот же источник
  правды, что и веб (дашборд/финансы/P&L-отчёт).
- Починка (`npm run tg:setup`, `scripts/telegram-setup.ts`): идемпотентно
  вызывает `setWebhook`/`setChatMenuButton`(`web_app` → `/tg`)/`setMyCommands`
  через Bot API по `TELEGRAM_BOT_TOKEN`+`NEXT_PUBLIC_SITE_URL` из `.env`.
  Перезапускать при смене домена или токена.
- Добавлено: команды `/help`, `/add` (инлайн-меню быстрых операций),
  `/invoices` + `/pay <№>` (дебиторка/пометка оплаты — тот же `recordPayment`
  каскад, что и веб, идемпотентен). Инлайн-кнопка «Открыть приложение» на
  `/start`/`/help` (отдельно от persistent menu button — это webApp-кнопка в
  клавиатуре сообщения). Mini App: новый модуль `/tg/invoices` (список
  неоплаченных + «Отметить оплаченным»), добавлен в домашний экран и нижнюю
  навигацию.
- Фото чека по-прежнему на Telegram CDN, не Google Drive — SA credentials всё
  ещё не подключены (см. выше и Этап 5); это не менялось в промпте D.

### Модуль «Сметы и Счета» — иерархия работа→материалы (после Mini App, 2026-08-09)
Развитие Этапа 6: `QuoteItem`/`InvoiceItem` (плоские позиции) **заменены полностью**
на `QuoteJob`→`QuoteMaterial` и `InvoiceJob`→`InvoiceMaterial` (родитель-работа,
дети-материалы, нумерация 1/1.1/1.2 в UI и PDF). Старые плоские модели удалены из
схемы — 2 тестовых пресмета и 1 счёт со старой структурой были снесены при
`prisma db push --accept-data-loss` (осознанное решение пользователя, детализация
осталась только в уже сгенерированных PDF).
- Общий парсинг/сборка работ — `lib/crm/documentJobs.ts` (`parseJobsInput`,
  `jobsToCreateInput`), используется и в `/api/crm/quotes`, и в `/api/crm/invoices`
  (POST), чтобы Decimal-логика (материал: qty×price; работа: сумма материалов +
  ручной `laborCost`; jobsTotal/materialsTotal/subtotal/IVA/IRPF/total) не
  дублировалась и не расходилась между документами.
- `Quote`/`Invoice` получили снапшот-поля `jobsTotal`/`materialsTotal` в дополнение
  к существующему `subtotal` (= их сумма) — PDF и все detail-страницы показывают
  «Итого работа» / «Итого материалы» отдельно, это и было целью фичи (клиент видел
  общую сумму «Материалы», не видел из чего складывается — теперь видит).
- Материал может ссылаться на `InventoryItem` (`inventoryItemId`, автокомплит в
  конструкторе подтягивает `sellPrice`) ИЛИ быть чисто ручным — оба пути не
  списывают склад при создании документа (это план, не движение; списание —
  через задачу планировщика, см. заметку по материалам задач выше).
- PDF (`lib/crm/pdf.tsx`): `Image` из `@react-pdf/renderer` рендерит
  `companyInfo.logoUrl` в шапке, если он задан в настройках — без логотипа шапка
  просто без лого, не ломается. Строка подписи «Client signature»/«Conforme el
  cliente» и т.п. — только для пресметов (`kind: 'quote'`), у счетов вместо неё
  дисклеймер про gestor'а, как было.
- Живой предпросмотр конструктора (`DocumentBuilder.tsx`) пересчитывает всё на
  клиенте через `decimal.js` идентично серверной логике — сервер всё равно
  пересчитывает и сохраняет как источник истины (клиентский расчёт только для UX).
- Протестировано вживую end-to-end: создание пресмета (работа + материал со

  клиента (полная детализация видна) → принятие клиентом → «Создать счёт из

### Заметка по Этапу 6 (важно для будущих правок PDF/email-роутов)
`@react-pdf/renderer` ломается с `React error #31`, если модуль, использующий его
JSX (`lib/crm/pdf.tsx`), импортируется из `app/api/**/route.ts`. Причина: Next
резолвит `react`/`react/jsx-runtime` под условием `react-server` для всего графа
`app/`, а react-pdf ожидает полный клиентский React. Поэтому PDF- и email-роуты
(`.../pdf`, `.../send` для quotes и invoices) живут в `pages/api/crm/...`
(Pages Router), а не в `app/api/crm/...`. Не переносить их обратно в `app/api`
без повторной проверки. Шрифт Roboto (кириллица + латиница с диакритикой)
зашит в `public/fonts/` — не заменять на fetch с Google Fonts на рантайме.

### Заметка по производительности аналитики (аудит-промпт 3, масштабирование)
Аудит указал, что `computeCashSummary`/маржа-функции агрегируют всю историю
компании без `from/to` и растут линейно с годами данных. Разобрался детально
перед тем, как что-то менять — картина не совсем такая, как в формулировке:
- `marginByBoat`/`marginByClient`/`marginByWorkType` (`lib/crm/services/profitability.ts`)
  **уже** принимают `from`/`to` и **уже** вызываются с границами периода
  везде, где грузятся вместе с дашбордом/отчётами (`reports/page.tsx`,
  `reports/pl/page.tsx` — always год/месяц). `computeBoatMargin`/
  `computeClientMargin` (единственное число, для страниц лодки/клиента) не
  ограничены датой намеренно — это pеальный лайфтайм-итог по ОДНОЙ записи,
  а не скан по всей компании, размер не растёт с историей компании в целом.
- Единственная реально неограниченная по времени функция — `computeCashSummary`
  (`lib/crm/services/cash.ts`), вызывается на дашборде/финансах/P&L. Это
  осознанно: касса — это **баланс на сейчас**, а не метрика за период, обрезать
  её по текущему году значило бы показывать неверную цифру (баланс обнулялся
  бы каждый январь). Period-bound здесь в принципе некорректен как решение.
- Индексы под её 4 агрегата (`FinanceEntry`/`CapitalEntry` — `(companyId, type,
  date)`, `VatEntry` — `(companyId, direction, date)`, `Invoice` —
  `(companyId, status)`) **уже есть** в схеме — не пришлось добавлять новые.
- Проверил реальный объём: на момент аудита 110 строк `FinanceEntry`, 0
  `CapitalEntry`/`VatEntry`. При таких объёмах (и ещё долго — Postgres
  агрегирует индексированные тысячи строк за миллисекунды) это не текущая
  проблема, а задел на будущий рост, каким его и описал сам промпт.
- **Не стал** строить материализованный кэш/снапшот кассы (пред­ложенный
  промптом как «при необходимости») — концептуально он завязан на границу
  «все данные раньше даты X гарантированно не изменятся», а это гарантирует
  только `PeriodLock` (см. FIX_2), и только если периоды закрыты БЕЗ пропусков
  от начала истории — при этом периоды можно переоткрыть (сам же и добавил
  эту кнопку как предохранитель), что требует инвалидации кэша на каждый
  reopen. Тихий баг в этой логике означает молча неверный баланс кассы,
  которым владелец пользуется для решений — тут цена ошибки существенно
  выше цены ещё не наступившей проблемы с производительностью. План на
  будущее, когда объём данных реально станет проблемой (десятки-сотни тысяч
  строк, ощутимая задержка дашборда): таблица `CashSnapshot` (одна строка на
  компанию — суммы income/expense/salary/reinvested/vat/irpf + `asOf`),
  обновляемая при закрытии периода ТОЛЬКО если закрытые периоды образуют
  непрерывный префикс от начала истории (иначе `asOf` не двигать), полностью
  сбрасываемая (не пересчитываемая на лету — проще и безопаснее) при
  реоткрытии любого периода; `computeCashSummary` = снапшот + живой агрегат
  по датам `>= asOf`.
