# Хранение фискальных документов (retention)

## Требование

Испания требует хранить документы, значимые для налогового и коммерческого
учёта (facturas emitidas/recibidas, IVA, бухгалтерские записи), определённый
срок после их выпуска/операции:

- **4 года** — общий срок давности налоговых обязательств по Ley General
  Tributaria (право налоговой затребовать документы за этот период).
- **6 лет** — срок хранения коммерческих книг и документов по Código de
  Comercio (art. 30) — более консервативная планка, которую на практике
  рекомендуют gestor'ы как безопасный минимум, а не только 4 года.

Это НЕ юридическая консультация — точный срок и любые нюансы (например,
удлинение срока при незакрытой налоговой проверке) уточнять у гестора
компании. Ниже — техническая часть: что в системе является «фискальным
документом» и как обеспечивается его доступность все эти годы.

## Что в системе является фискальным документом

| Что | Модель Prisma | Где физически |
|---|---|---|
| Счёт (factura) | `Invoice` (кроме `DRAFT`) + `InvoiceJob`/`InvoiceMaterial` | Postgres (Supabase) |
| Пресмет, ставший счётом | `Quote` (принятый, откуда счёт создан кнопкой «Создать счёт из пресмета») | Postgres |
| IVA repercutido/soportado | `VatEntry` | Postgres |
| Учётная операция (доход/расход/зарплата) | `FinanceEntry` | Postgres |
| Аудит-след операций | `AuditLog` | Postgres |
| PDF счёта/пресмета | не хранится файлом — рендерится на лету из `Invoice`/`InvoiceJob`/`InvoiceMaterial` (`lib/crm/pdf.tsx`) при каждом открытии `/pdf` | генерируется из строк выше, поэтому ретеншен = ретеншен этих строк в БД |

Черновики (`Invoice.status === 'DRAFT'`) фискальными документами не
являются — у них нет сквозного номера (`number`/`year`/`sequenceNum` пустые
до выпуска, см. `lib/crm/numbering.ts`) и их можно удалить безвозвратно
(`DELETE /api/crm/invoices/[id]`, только для `DRAFT`).

## Как ретеншен уже обеспечен технически

**Выпущенный счёт никогда не удаляется физически.** `DELETE
/api/crm/invoices/[id]` (`app/api/crm/invoices/[id]/route.ts`) для любого
статуса кроме `DRAFT` не делает `prisma.invoice.delete` — переводит счёт в
`CANCELLED` (со сторно уже зачтённого дохода через `refundPayment`, если
счёт был оплачен). Строка остаётся в базе навсегда, видна в истории,
сохраняет свой номер (сквозная нумерация не переиспользуется — см.
`ARCHITECTURE.md`/`numbering.ts`). То же для `FinanceEntry`/`VatEntry` —
операции не редактируются и не удаляются напрямую, только компенсируются
сторно-записью (см. `CLAUDE.md`, раздел про деньги).

**Ежедневный JSON-бэкап (`db-backups/` в Supabase Storage, см.
`docs/backup-recovery.md`) не имеет автоматической очистки.** Ни в
`lib/crm/services/backup.ts`, ни в cron-роуте (`app/api/crm/cron/backup/
route.ts`) нет кода, удаляющего старые файлы бакета — файлы копятся
бессрочно. Это НЕ настроенная политика хранения (нет явного lifecycle-правила
на бакете), а отсутствие удаляющего кода — то есть по умолчанию ничего не
удаляется раньше срока, потому что не удаляется вообще.

## Что НЕ является ретеншеном фискальных документов (важное различие)

Уровень 1 бэкапов из `docs/backup-recovery.md` — встроенный PITR/бэкапы
Supabase (по умолчанию 7–14 дней глубины на платных планах) — **это
операционное аварийное восстановление, не механизм хранения фискальных
документов**. Не путать: если этот PITR-бэкап истечёт и будет перезаписан
через 2 недели, это никак не нарушает 4–6-летний ретеншен, потому что живая
строка `Invoice`/`VatEntry` продолжает существовать в проде — ретеншен
держится на строках в текущей БД (плюс их ежедневный JSON-слепок), а не на
глубине PITR-истории.

## Ограничения на будущие изменения (чтобы не нарушить ретеншен случайно)

Если в будущем понадобится любая из следующих фич — **явно учитывать
4–6-летний ретеншен фискальных документов**, не удалять данные моложе этого
срока:

- **GDPR-удаление данных клиента по запросу.** Право на удаление (right to
  erasure) не абсолютно — статья 17(3)(b) GDPR прямо допускает отказ, если
  обработка нужна для выполнения юридического обязательства (в т.ч.
  налогового хранения документов). На практике: можно анонимизировать
  персональные поля клиента (имя/телефон/email), но НЕЛЬЗЯ удалять сам
  `Invoice`/`VatEntry`/`FinanceEntry`, пока не истёк срок хранения —
  сейчас в системе такой функции нет, но если появится, это должно быть
  задокументировано как её ограничение с самого начала.
- **Ротация/очистка бакета `db-backups/`** — если объём когда-нибудь станет
  проблемой, решение — архивация в более холодное/дешёвое хранилище, а не
  прямое удаление файлов моложе 6 лет. Не добавлять cron/lifecycle-правило,
  удаляющее файлы бакета по возрасту, без сверки с этим сроком.
- **Смена Supabase-плана на более дешёвый с меньшим PITR** — безопасно для
  ретеншена фискальных документов (см. раздел выше), но не безопасно для
  операционного аварийного восстановления — оценивать отдельно.

## Проверено

- Прочитан код `DELETE /api/crm/invoices/[id]` — подтверждено: выпущенный
  счёт (`status !== 'DRAFT'`) никогда не проходит `prisma.invoice.delete`,
  только `CANCELLED` с сохранением строки.
- Прочитан `lib/crm/services/backup.ts` и оба cron-роута бэкапа — в коде нет
  логики удаления/очистки старых файлов `db-backups/`.
- Поиск по репозиторию на предмет lifecycle-правил/конфигурации Supabase
  Storage (`.toml`, `supabase/` каталог) — ничего не найдено; политика
  бакета не задана как инфраструктура-как-код, значит удаление файлов
  раньше срока не может произойти автоматически через деплой.
