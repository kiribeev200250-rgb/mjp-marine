# Бэкапы и восстановление БД

Два независимых уровня защиты. Уровень 1 — обязательный, настраивается один
раз в Supabase и защищает всё (включая Storage, роли, конфигурацию проекта).
Уровень 2 — дополнение этого приложения: ежедневный JSON-снапшот всех таблиц,
на случай если понадобится восстановить только данные (например, откатить
случайно испорченную запись без отката всего проекта).

## Уровень 1 — встроенные бэкапы Supabase (основная защита)

Supabase Postgres по умолчанию делает ежедневные бэкапы, но глубина хранения
и Point-in-Time Recovery (PITR — восстановление на любую секунду за последние
N дней, а не только на полночь) зависят от плана и настроек проекта.

**Как включить / проверить:**

1. Зайти в [Supabase Dashboard](https://supabase.com/dashboard) → выбрать проект.
2. Слева: **Database** → **Backups**.
3. Убедиться, что план проекта поддерживает нужную глубину — на Pro и выше
   доступен PITR (обычно 7–14 дней, настраивается). На Free — только
   ежедневные бэкапы с коротким хранением.
4. Если нужен PITR — включить его в этом разделе (может требовать апгрейда
   плана). Задать желаемый retention (сколько дней хранить).
5. Сохранить.

**Как восстановиться (аварийный сценарий — потеряна/испорчена вся БД):**

1. Database → Backups → выбрать точку восстановления (конкретный бэкап или,
   если включён PITR, конкретный момент времени).
2. Supabase создаёт новую БД/проект с данными на этот момент, либо
   восстанавливает поверх текущей — **внимательно прочитать предупреждение
   в диалоге**, это необратимая операция, откатывающая ВСЁ состояние проекта.
3. После восстановления — обновить `DATABASE_URL`/`DIRECT_URL` в Vercel
   (Project Settings → Environment Variables), если Supabase выдал новые
   реквизиты подключения, и передеплоить.

**Важно:** это единственный способ восстановить проект целиком (включая
Storage-бакеты, если они были повреждены). Уровень 2 ниже восстанавливает
только содержимое таблиц Prisma.

## Уровень 2 — ежедневный JSON-снапшот (это приложение)

Дополнительно, независимо от Supabase, приложение каждую ночь выгружает
все строки всех таблиц в один JSON-файл и кладёт в приватный бакет Supabase
Storage `db-backups/` (Vercel Cron, `0 3 * * *` — см. `vercel.json`,
роут `app/api/crm/cron/backup/route.ts`). Полезно как:

- второй, независимый от Supabase-инфраструктуры экземпляр данных;
- инструмент для точечного восстановления одной случайно удалённой/
  испорченной записи или таблицы без отката всего проекта.

Логика — `lib/crm/services/backup.ts`:
`exportDatabaseBackup()` (выгрузка), `restoreDatabaseBackup()` (восстановление,
таблица за таблицей в порядке, безопасном для внешних ключей).

**Ручной запуск бэкапа** (например, перед рискованной операцией):

```bash
npm run db:backup
```

Выведет имя файла и статистику (сколько таблиц/строк/КБ). Файл появится в
Supabase Storage → db-backups.

**Скачать конкретный бэкап:** Supabase Dashboard → Storage → db-backups →
выбрать файл → Download. Это обычный JSON, можно открыть текстовым
редактором и найти нужную запись вручную для точечной проверки.

**Восстановить из JSON-снапшота:**

```ts
import { restoreDatabaseBackup } from '@/lib/crm/services/backup'

const payload = JSON.parse(fs.readFileSync('путь/к/файлу.json', 'utf-8'))

// Восстановить всё (безопасно — skipDuplicates не тронет уже существующие строки)
await restoreDatabaseBackup(payload)

// Или восстановить только конкретные таблицы (точечное восстановление)
await restoreDatabaseBackup(payload, { onlyModels: ['financeEntry', 'vatEntry'] })
```

Восстановление идёт в порядке, безопасном для внешних ключей (родительские
таблицы раньше зависимых — см. `MODELS_IN_DEPENDENCY_ORDER` в
`lib/crm/services/backup.ts`), одной транзакцией, с `skipDuplicates: true` —
повторный запуск на непустой БД не задвоит существующие строки (совпадающие
по `id` строки просто пропускаются).

**Ограничение:** это восстановление ДАННЫХ (таблицы Prisma), не структуры БД.
Схема (`CREATE TABLE`, индексы, типы) восстанавливается отдельно из
`prisma/schema.prisma` командой `npx prisma db push` — она уже версионируется
в git, поэтому отдельно не бэкапится.

## Проверено вживую (2026-08-11)

Механизм экспорта/восстановления протестирован на реальной базе:

1. Создана одноразовая тестовая запись (`CapitalEntry`, `ZZTEST`) в реальной
   базе.
2. `exportDatabaseBackup()` — запись подтверждена в снапшоте.
3. Запись удалена из базы (симуляция потери данных) — подтверждено, что её
   больше нет.
4. `restoreDatabaseBackup(payload, { onlyModels: ['capitalEntry'] })` —
   восстановлена.
5. Все поля восстановленной записи посимвольно совпали с оригиналом.
6. Тестовая запись удалена окончательно (уборка за собой).

Отдельно `npm run db:backup` запущен вживую против реальной БД — выгрузил
37 таблиц / 400 строк и успешно загрузил в Supabase Storage.

**Не проверено (требует отдельного окружения):** полное восстановление в
СВЕЖИЙ, пустой Supabase-проект «с нуля» — для этого нужен второй проект
Supabase, который может создать только владелец аккаунта. Процедура для
такой проверки:

1. Создать новый (тестовый) проект в Supabase.
2. Прогнать `npx prisma db push` против него, чтобы создать схему.
3. Указать его `DATABASE_URL`/`DIRECT_URL` во временном `.env.test`.
4. Запустить восстановление (`restoreDatabaseBackup`) со свежим экспортом
   из продакшена, подключившись к тестовой базе.
5. Сверить количество строк по таблицам с оригиналом.

Рекомендуется сделать эту проверку один раз перед боевым запуском и затем
раз в несколько месяцев.
