# Модель безопасности CRM

## RLS (Row Level Security) — что реально защищает, а что нет

`ARCHITECTURE.md` описывает "строгие RLS-политики по `company_id`" на
CRM-таблицах как модель — но это описывает *возможность*, а не текущую
границу защиты. Важно понимать разницу:

**Prisma-соединение (весь сервер, все route handlers и Telegram-бот) ходит в
Postgres под ролью, у которой `rolbypassrls: true`.** Это стандартное
поведение для роли, через которую Prisma/Supabase выдают connection string
(`postgres`/service-role уровня доступа) — она физически обходит любые RLS-
политики, даже если те определены на таблицах. Это значит:

- RLS **не является** защитой в глубину для этого приложения. Изоляция
  между компаниями (`companyId`) и права ролей (`ADMIN`/`EMPLOYEE`,
  `lib/crm/permissions.ts`) целиком держатся на серверном коде — `where:
  { companyId: session.user.companyId }` в каждом запросе и
  `requirePermission(...)`/`hasPermission(...)` перед каждой мутацией.
- Если в каком-то route handler'е забыть добавить `companyId` в `where` —
  RLS это не поймает. Единственная защита — дисциплина в коде и ревью.
- Определять RLS-политики на CRM-таблицах сейчас **не имеет смысла как
  защита** (хотя не вредно как документация намерения) — единственное
  Postgres-соединение приложения их не видит.

**Когда это станет важно:** если появится ВТОРОЙ путь к базе, не через
Prisma-соединение сервера — например, прямой Supabase JS-клиент из браузера
(anon key) для какой-то будущей фичи realtime, или сторонний интеграционный
сервис с собственным доступом к БД. В этот момент:

1. Такое соединение почти наверняка НЕ будет иметь `rolbypassrls` (anon/
   authenticated роли Supabase — обычные роли, RLS для них действует).
2. Нужно будет завести реальные RLS-политики по `company_id` на всех
   затронутых таблицах для этой роли — иначе она либо ничего не увидит
   (RLS без политик = запрет всего), либо, если политики скопированы
   небрежно, увидит чужие компании.
3. Права этого нового пути проверяются ОТДЕЛЬНО от прав Prisma-соединения —
   нельзя полагаться на то, что "раз для сервера работает, значит и здесь
   правильно".

## Проверка прав — где она реально происходит

- Каждый `route.ts` в `app/api/crm/**` обязан вызвать `requirePermission`
  (бросает) или `hasPermission` (проверить руками) из `lib/crm/permissions.ts`
  ДО любой мутации, и добавить `companyId: session.user.companyId` в
  каждый `where`. UI (`hasPermission` в серверных компонентах, скрытие
  кнопок) — это удобство, не граница безопасности; настоящая граница —
  сервер.
- Telegram-бот и Mini App повторяют ту же проверку через `can()`/
  `hasPermission()` со своим способом резолвинга сессии
  (`lib/crm/telegram/auth.ts`, `lib/crm/telegram/webapp-auth.ts`) — тот же
  принцип, отдельная реализация сессии.
- Систематического автотеста "неавторизованный доступ к каждому модулю"
  (запрос без сессии / с недостаточными правами → всегда 401/403, никогда
  200 с чужими данными) пока нет — это отдельная задача (тест-сьют,
  запланирован отдельным промптом).

## Секреты

- Все ключи (Google, Facebook, Telegram, Resend, Supabase service role) —
  только в `.env` / Vercel Environment Variables, не в git (см.
  `.env.example` — шаблон без значений).
- `SUPABASE_SERVICE_ROLE_KEY` — это ключ, который обходит RLS по определению
  (аналог `rolbypassrls` выше, но для Supabase Storage/Auth API, а не
  Postgres-соединения напрямую) — используется только на сервере
  (`lib/crm/storage.ts`, роуты фото задач), никогда не передаётся в браузер.
